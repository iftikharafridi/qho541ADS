Why this matters

Last week the Online Shop database learned to reject impossible data: an order for a customer who does not exist, a negative price. It still accepts plenty of data that is possible but wrong for the business. A customer can order 10 cheddars when 4 are in stock. A delivered order can be quietly edited. Stock levels drift away from what was actually sold. Nobody can say who changed a price, or when.

Real systems handle these rules with triggers: small programs stored inside the database that run automatically whenever data changes. Because they live in the database, they apply to every program that touches the data: the Tkinter app you build in Week 4, an import script, or someone typing SQL into DB Browser.

Retail

Reserve stock as items go into an order; raise a reorder alert when stock runs low.

Banking

Record every change to an account in an append-only audit table that regulators can inspect.

Healthcare

Log every access to or change of a patient record, as data-protection law requires.

Workflow

Stop an invoice that has been paid from being edited, or an order from moving backwards through its stages.

What is a trigger?

A trigger is a named block of SQL that the database runs automatically when a specified change happens to a specified table. You never call a trigger yourself: the database fires it. Every trigger follows the event → condition → action (ECA) pattern:

PartQuestion it answersOnline Shop example
EventWhich change on which table?INSERT ON order_item
TimingBefore or after the row is changed (or instead of it)?AFTER
Condition (optional)Should it run for this row?WHEN NEW.quantity > 0
ActionWhat SQL runs?UPDATE inventory SET qty_in_stock = qty_in_stock - NEW.quantity …

Benefits

  • Rules live in one place. Every program that changes the data obeys them; you do not re-code them in each application.
  • Easier maintenance. Change the rule once, in the database.
  • Consistency. Related changes (sale and stock, change and audit row) happen in the same transaction: both or neither.
  • Performance in client–server systems. The work happens next to the data, with no extra network round trips.

Drawbacks

  • Hidden behaviour. A simple INSERT may change five tables, which surprises anyone who does not know the triggers exist.
  • Harder to debug, because they run automatically and invisibly.
  • Performance cost on every affected row, especially with cascades.
  • Logic split between application and database if used carelessly.

Trigger or application code?

Use a trigger for rules that must hold no matter who changes the data (stock must match sales; audits must not be skipped). Keep presentation and user-interaction logic (messages, screens, workflows involving a person) in the application. Use a simple CHECK constraint instead of a trigger when the rule only involves the row itself (price >= 0).

Trigger syntax in SQLite


CREATE [TEMP] TRIGGER [IF NOT EXISTS] trigger_name
    { BEFORE | AFTER | INSTEAD OF }
    { INSERT | UPDATE [OF column, …] | DELETE }
    ON table_or_view_name
    [FOR EACH ROW]
    [WHEN condition]
BEGIN
    statement;          -- INSERT, UPDATE, DELETE or SELECT
    statement;          -- as many as you need, each ending with ;
END;
trigger_name
Must be unique in the database. A naming convention such as trg_table_purpose makes triggers easy to find.
BEFORE / AFTER
Whether the action runs before or after the row is changed. On tables only.
INSTEAD OF
Replaces the change entirely. On views only (see below).
UPDATE OF col, …
Fire only when one of these columns appears in the SET list of the UPDATE.
FOR EACH ROW
The trigger runs once per affected row. SQLite only supports row-level triggers, so this clause is optional and implied.
WHEN
A condition checked for each row; if it is false (or NULL) the body is skipped for that row.
BEGIN … END
The body: one or more SQL statements. There are no variables, IF statements or loops; use WHEN, CASE and subqueries instead.

Managing triggers


-- List every trigger, with the table it belongs to

There is no ALTER TRIGGER in SQLite: to change a trigger, DROP TRIGGER IF EXISTS name; and create it again. Dropping a table also drops its triggers. In DB Browser for SQLite, triggers appear under Database Structure → Triggers.

OLD and NEW

Inside a trigger, NEW and OLD refer to the row being changed. Which ones exist depends on the event:

EventOLD.columnNEW.columnTypical use
INSERT✗ (no old row)✓ the row being addedCheck or react to the new data
UPDATE✓ values before the change✓ values after the changeCompare: what changed, by how much?
DELETE✓ the row being removed✗ (no new row)Undo its effects; archive it

A mistake SQLite does not catch until it runs

A trigger that uses NEW in a DELETE trigger (or OLD in an INSERT trigger) is created without any error. It only fails when it fires, with no such column: NEW.quantity. Always test every trigger by actually firing it.

BEFORE, AFTER and INSTEAD OF: the execution flow

What exactly happens when one statement fires triggers? For each row the statement touches, SQLite runs the steps below in order. This flow is the most useful thing to understand when a trigger does something unexpected.

TimingRunsUse it to…Online Shop example
BEFOREbefore constraints are checked and the row is writtenvalidate, and refuse bad changes with RAISErefuse an order line when stock is too low
AFTERafter the row has been writtenchange other tables as a consequence; write logsreduce stock; record a stock movement
INSTEAD OFin place of the change (views only)make a view behave as if it were updatableinsert an order line by product name

SQLite-specific: BEFORE triggers cannot change the row

In MySQL or PostgreSQL a BEFORE trigger often fixes the incoming row (SET NEW.price = …). SQLite does not allow assignment to NEW. A BEFORE trigger can only check and refuse. To fill in a value, use an AFTER trigger that UPDATEs the new row, a column DEFAULT, or an INSTEAD OF trigger on a view. The SQLite documentation also warns against a BEFORE UPDATE or DELETE trigger changing the very row being updated or deleted: the result is undefined, so use AFTER.

The original slides gave two solutions:

Solution 1: CASE inside the body


CREATE TRIGGER trg_check_stock_v1
BEFORE INSERT ON order_item
BEGIN
    SELECT CASE
        WHEN (SELECT qty_in_stock FROM inventory
              WHERE product_id = NEW.product_id) < NEW.quantity
        THEN RAISE(ABORT, 'Not enough stock')
    END;
END;

Solution 2: a WHEN clause (preferred)


CREATE TRIGGER trg_check_stock_v2
BEFORE INSERT ON order_item
FOR EACH ROW
WHEN NEW.quantity > (SELECT qty_in_stock FROM inventory
                     WHERE product_id = NEW.product_id)
BEGIN
    SELECT RAISE(ABORT, 'Not enough stock');
END;

Both work. Solution 2 is easier to read, because the condition is in the trigger’s header, and the body only runs when it is needed. Try it:

The NULL trap

If a product has no inventory row, the subquery returns NULL, 10 > NULL is NULL (not true), and Solution 2 lets the order through. The shop’s real trigger uses COALESCE((SELECT …), 0) so a missing stock record counts as zero stock.

WHEN conditions and RAISE()

Writing good WHEN conditions

  • Fire only on real changes. UPDATE OF price fires whenever price appears in the SET list, even if the value is the same. Add WHEN NEW.price <> OLD.price.
  • Compare NULL-safely. OLD.phone <> NEW.phone is NULL when either is NULL, so a change to or from NULL would be missed. Use OLD.phone IS NOT NEW.phone.
  • Detect crossings, not states. A reorder alert should be raised when stock falls to the reorder level, not on every later sale: WHEN NEW.qty_in_stock <= NEW.reorder_level AND OLD.qty_in_stock > OLD.reorder_level.

RAISE() options

RAISE() can only be used inside a trigger. Its message must be a plain string literal, such as 'Not enough stock'; it cannot be built from NEW values in the SQLite versions used in this module.

FormEffectIn Python
RAISE(ABORT, 'msg')Stops the statement and undoes all of its changes, including those made by triggers. Earlier statements in the same transaction are kept. The usual choice.sqlite3.IntegrityError: msg
RAISE(FAIL, 'msg')Stops the statement but keeps rows it had already changed (e.g. the first rows of a multi-row INSERT).IntegrityError
RAISE(ROLLBACK, 'msg')Rolls back the whole transaction, not just this statement.IntegrityError, transaction ended
RAISE(IGNORE)Silently skips the current row and carries on with the next; no error.no error, row not changed

Audit logging

An audit trail records who changed what, when, from what and to what. Triggers are ideal for this because they cannot be bypassed by forgetting to call a logging function.

  • What to record: the table and key of the changed row, the action, the old and new values, and a timestamp (datetime('now') is UTC).
  • No foreign keys on audit tables. A log must keep its rows even after the audited row is deleted, so audit_log has none.
  • Who made the change? SQLite has no user accounts, so it has no CURRENT_USER. The application must record the user, for example by writing to an changed_by column. Client–server databases can log the database user automatically.
  • Personal data. Audit logs of customer details are themselves personal data under UK GDPR: decide how long to keep them, and who may read them.

CREATE TRIGGER trg_customer_audit_update
AFTER UPDATE OF email, phone, address_line, postcode ON customer
FOR EACH ROW
WHEN OLD.email IS NOT NEW.email OR OLD.phone IS NOT NEW.phone
  OR OLD.address_line IS NOT NEW.address_line OR OLD.postcode IS NOT NEW.postcode
BEGIN
    INSERT INTO audit_log (table_name, action, row_key, details)
    VALUES ('customer', 'UPDATE', 'customer_id=' || NEW.customer_id,
            CASE WHEN OLD.email IS NOT NEW.email
                 THEN 'email: ' || OLD.email || ' -> ' || NEW.email || '; ' ELSE '' END ||
            CASE WHEN OLD.phone IS NOT NEW.phone
                 THEN 'phone: ' || IFNULL(OLD.phone, 'NULL') || ' -> ' || IFNULL(NEW.phone, 'NULL') || '; ' ELSE '' END ||
            CASE WHEN OLD.address_line IS NOT NEW.address_line
                 THEN 'address: ' || OLD.address_line || ' -> ' || NEW.address_line || '; ' ELSE '' END ||
            CASE WHEN OLD.postcode IS NOT NEW.postcode
                 THEN 'postcode: ' || OLD.postcode || ' -> ' || NEW.postcode || '; ' ELSE '' END);
END;

Cascading, recursion and firing order

Cascading triggers
A trigger’s action can fire other triggers, as when a sale updates inventory, which raises a reorder alert. SQLite allows this, up to a depth limit of 1000.
Recursive triggers
A trigger that (directly or indirectly) fires itself, e.g. an AFTER UPDATE on inventory that updates inventory. SQLite blocks this by default (PRAGMA recursive_triggers is OFF). Do not turn it on unless you are sure the recursion stops.
Foreign-key actions fire triggers
ON DELETE CASCADE deletes child rows as if by a DELETE statement, so their DELETE triggers run. Deleting a pending order in shop_v2 therefore returns its stock through trg_order_item_removed.
Several triggers on one event
The order is not guaranteed. Current SQLite versions happen to run the most recently created first, but do not rely on it: write triggers that do not depend on each other’s order.

INSTEAD OF triggers on views

A view is a stored query that behaves like a read-only table (Week 3 covers views in depth). You cannot INSERT into a view directly, because it has no rows of its own. An INSTEAD OF trigger tells SQLite what to do instead, usually by changing the underlying tables.


CREATE VIEW v_order_lines AS
SELECT oi.order_id, p.name AS product, oi.quantity, oi.unit_price
FROM   order_item AS oi
JOIN   product    AS p ON p.product_id = oi.product_id;

CREATE TRIGGER trg_v_order_lines_insert
INSTEAD OF INSERT ON v_order_lines
FOR EACH ROW
BEGIN
    SELECT RAISE(ABORT, 'Unknown product name')
    WHERE NOT EXISTS (SELECT 1 FROM product WHERE name = NEW.product);

    INSERT INTO order_item (order_id, product_id, quantity, unit_price)
    SELECT NEW.order_id, product_id, NEW.quantity, price
    FROM   product
    WHERE  name = NEW.product;
END;

Notice two techniques: SELECT RAISE(…) WHERE … raises only when the WHERE finds a row, which works like an IF; and the INSERT … SELECT fills in unit_price from the product table, because SQLite will not let a trigger assign NEW.unit_price.

Why the original slides mention SQL Server functions

Some older module material used SQL Server syntax. SQL Server has no BEFORE triggers and processes a whole statement at once through the inserted and deleted tables. Code written for it will not run in SQLite, and the reverse is also true. Everything in this module is SQLite.

Triggers from Python

Your Tkinter application (Week 4 onwards) never calls a trigger: it just runs INSERT, UPDATE and DELETE statements, and the triggers fire. What it must do is handle the errors they raise and show a friendly message. trigger_demo_v2.py shows the pattern.


def add_line(con, order_id, product_id, qty, price):
    """Insert one order line; the triggers decide whether it is allowed."""
    try:
        with con:                                   # commit, or roll back on error
            con.execute(
                "INSERT INTO order_item (order_id, product_id, quantity, unit_price) "
                "VALUES (?, ?, ?, ?)",
                (order_id, product_id, qty, price))
        print(f"  OK: added {qty} x product {product_id} to order {order_id}")
    except sqlite3.IntegrityError as err:           # RAISE(ABORT, ...) arrives here
        print(f"  Refused by a trigger: {err}")     # in Tkinter: messagebox.showerror(...)
  • RAISE(ABORT, 'msg') becomes sqlite3.IntegrityError whose text is your message, so write messages a user can understand.
  • with con: makes the statement and everything its triggers did a single transaction.
  • The demo copies the database into memory with disk.backup(mem), so you can run it again and again without changing shop_v2.db.

Debugging and common mistakes

A debugging routine

  1. Confirm the trigger exists and is the version you think: SELECT sql FROM sqlite_master WHERE type='trigger' AND name='…';
  2. Test the WHEN condition on its own as a SELECT, replacing NEW.x with real values (or use IIF).
  3. Fire it with one row and look at every table it should change, before and after (just like the trigger lab).
  4. Add a temporary log: INSERT INTO debug_log VALUES ('reached step 2', NEW.quantity); inside the body, then remove it.
  5. Check for other triggers on the same table that might interfere: SELECT name FROM sqlite_master WHERE type='trigger' AND tbl_name='order_item';
MistakeSymptomFix
Fixed values in the body (SET qty_in_stock = 99 WHERE product_id = 9)Works for one test, wrong for every other rowUse NEW./OLD. values

No WHEN on an UPDATE triggerLogs or adjusts even when nothing really changedWHEN NEW.x IS NOT OLD.x

Relying on the order of two triggersWorks today, breaks after a rebuildCombine them, or make them independent

Summary and next steps

  • A trigger is event → (condition) → action, fired automatically for each row.
  • BEFORE validates and refuses with RAISE; AFTER carries out consequences in other tables; INSTEAD OF makes views updatable.
  • INSERT has NEW, DELETE has OLD, UPDATE has both. Use UPDATE OF and WHEN so a trigger only fires when it should.
  • RAISE(ABORT) undoes everything the statement did, including other triggers’ work, and arrives in Python as IntegrityError.
  • SQLite triggers are row-level only, cannot assign NEW, have plain-SQL bodies and fire in an unguaranteed order.
  • Audit tables record old and new values and have no foreign keys.

Activity 2: Guided: stock control on INSERT

Write two triggers on shop_v1

Hints

Model answer (seminar/w2_stock_triggers.sql)

CREATE TRIGGER check_stock
BEFORE INSERT ON order_item
FOR EACH ROW
WHEN NEW.quantity > COALESCE((SELECT qty_in_stock FROM inventory WHERE product_id = NEW.product_id), 0)
BEGIN
    SELECT RAISE(ABORT, 'Not enough stock');
END;

CREATE TRIGGER reduce_stock
AFTER INSERT ON order_item
FOR EACH ROW
BEGIN
    UPDATE inventory SET qty_in_stock = qty_in_stock - NEW.quantity
    WHERE product_id = NEW.product_id;
END;

  3. Explain in one sentence why the UPDATE trigger needs both OLD and NEW, and why the DELETE trigger can only use OLD.
Model answer

CREATE TRIGGER adjust_stock
AFTER UPDATE OF quantity ON order_item
FOR EACH ROW
WHEN NEW.quantity <> OLD.quantity
BEGIN
    UPDATE inventory SET qty_in_stock = qty_in_stock - (NEW.quantity - OLD.quantity)
    WHERE product_id = NEW.product_id;
END;

CREATE TRIGGER return_stock
AFTER DELETE ON order_item
FOR EACH ROW
BEGIN
    UPDATE inventory SET qty_in_stock = qty_in_stock + OLD.quantity
    WHERE product_id = OLD.product_id;
END;

The change in stock depends on how the quantity changed (NEW − OLD), so the UPDATE trigger needs both. A deleted row has no new version, so only OLD exists. Extension: what should happen if the increase is larger than the stock? (Compare trg_order_item_check_amend in shop_v2.)

Activity 4: Keeping an order total up to date

The original Task 1 asked for an order_cost table maintained by triggers. Build order_total(order_id, total) and keep it correct whenever an order line is inserted, updated or deleted.

Discuss before you build

order_total stores a value that can be calculated from order_item, so it is denormalisation (Week 1). When is that worth it, and what could go wrong? Next week you will meet the alternative: a view that calculates totals on demand.

Hint: recalculate, don’t increment

Adding and subtracting amounts in each trigger works, but one mistake makes the total drift for ever. Recalculating with SELECT SUM(quantity * unit_price) FROM order_item WHERE order_id = … in every trigger is simpler and self-correcting.

Answers (seminar/w2_debugging_fixed.sql)
  1. Bug 1: fixed values. Every sale sets the stock of one hard-coded product (101, which does not even exist in our shop) to 99. Use qty_in_stock - NEW.quantity and WHERE product_id = NEW.product_id.

Glossary

Audit trail
An append-only record of changes: what, when, old and new values.
Cascading trigger
A trigger fired by another trigger’s action.
ECA
Event → condition → action: the structure of every trigger.
INSTEAD OF
A trigger that replaces an INSERT, UPDATE or DELETE on a view.
NEW / OLD
The row after / before the change, inside a row-level trigger.
RAISE()
Stops or skips the current change from inside a trigger (ABORT, FAIL, ROLLBACK, IGNORE).
Recursive trigger
A trigger that fires itself. Off by default in SQLite.
Row-level trigger
Runs once for every row a statement affects (the only kind in SQLite).
