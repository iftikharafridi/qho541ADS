Learning outcomes

  2. Compare relational and NoSQL databases and say when each is appropriate.

Why this matters

Most business data starts life in a spreadsheet. A small online shop might keep one sheet with a row per order: the customer’s name, address and phone, then each product, its price and supplier. It works until the shop grows. A customer moves house and the address is updated in one row but not in the other twelve, so a parcel goes to the wrong address. A product is discontinued, the rows that mention it are deleted, and the only record of its supplier goes with them. A data-protection request asks for everything held about one person, and it is scattered across hundreds of rows.

Normalisation is the systematic way to remove these problems before they happen, and an ER diagram is how database professionals communicate the result to clients, developers and examiners. Everything else in this module (triggers, views, the Tkinter application, XML backups) sits on top of the design you make this week. A weak design makes every later task harder.

Data, information and the DBMS

Data
Raw, unorganised facts with no context: 1001, 2025-09-25, 0.80, 4.
Information
Data that has been processed, organised and put into context so that it is meaningful and useful for a decision: “Jane Morris has placed three orders since September; her last one is still pending.”

The DIKW pyramid extends this idea: data plus context gives information; information plus meaning (patterns, comparisons, experience) gives knowledge; knowledge plus insight gives wisdom, meaning sound decisions. Databases work at the bottom two levels. Reports, analytics and people supply the rest.

The simplest store of data is a flat file: a single table, such as a spreadsheet, where each row is a record and each column an attribute. It is easy to build in Excel or Access, but it cannot express relationships without repeating data. That is the problem this week solves.

A database is an organised, shared collection of related data. A database management system (DBMS) is the software that stores that data and controls access to it. It enforces structure and integrity rules, runs queries, manages concurrent users and transactions, and recovers from failures.

Relational and NoSQL databases

The relational model was proposed by E. F. Codd at IBM in 1970. A relational database stores data in tables (relations) with a fixed schema. Tables are linked by key values and queried with SQL. Relational databases give strong integrity guarantees and ACID transactions (atomic, consistent, isolated, durable): ideal when many related rows must change together correctly, such as an order and its stock update.

NoSQL (“not only SQL”) is a family of non-relational databases designed for flexible or changing structure, very large scale, or particular data shapes. Amazon’s Dynamo and Google’s Bigtable papers inspired many of them. The four main families:

Relational (SQL)NoSQL
StructureFixed schema of tables, rows and columns, defined before data is addedFlexible: documents, key–value pairs, column families or graphs; structure can vary per record
RelationshipsForeign keys and JOINsUsually embedded or duplicated data (document), or first-class edges (graph)
Integrity & transactionsStrong: constraints and multi-row ACID transactionsVaries; many trade strict consistency for availability and scale
ScalingTraditionally scale up (a bigger server)Designed to scale out across many servers
Best forStructured, related business data such as orders, banking and enrolmentsHuge volumes, rapidly changing or semi-structured data, caching, social graphs
WeaknessesRigid with unstructured data; schema changes need planningWeaker or more complex querying across records; less mature integrity tooling

Precise terms

Cassandra and HBase are wide-column stores, not simple key–value stores. Neither is the same as a column-oriented relational database such as Vertica, which stores each column contiguously to speed up analytics. A BLOB (binary large object) is a data type for raw bytes such as images (Week 9). It is not another name for a document. You will meet a document format, XML, alongside SQLite in Week 7.

Keys

Super key
Any set of columns whose values are unique for every row, e.g. (customer_id, email).
Candidate key
A minimal super key: remove any column and it stops being unique. customer_id and email are both candidate keys of customer.
Primary key (PK)
The candidate key chosen to identify rows. Must be unique and never NULL. customer.customer_id.
Alternate key
A candidate key not chosen as the PK. Enforce it with UNIQUE (customer.email).
Composite key
A key made of two or more columns: order_item (order_id, product_id).
Natural vs surrogate
A natural key has real-world meaning (an e-mail, a car registration). A surrogate key is a meaningless number generated by the database (customer_id). Surrogates never change and stay short, which is why most tables in the shop use them.
Foreign key (FK)
A column whose values must match a primary (or unique) key in another table: orders.customer_id → customer.customer_id.

Integrity rules

  • Entity integrity: every row has a primary key value that is unique and not NULL.
  • Referential integrity: every foreign key value matches an existing key in the referenced table (or is NULL, if allowed).
  • Domain integrity: values are of the right kind and within allowed limits (NOT NULL, CHECK (price >= 0), DEFAULT).

Two SQLite surprises

1. Foreign keys are off by default. Every new connection must run PRAGMA foreign_keys = ON; or SQLite silently ignores every REFERENCES clause.

2. Non-integer primary keys can be NULL unless you also write NOT NULL (a historical quirk). INTEGER PRIMARY KEY columns are safe: they are the table’s row id and are filled in automatically.

Why normalise? Data anomalies

Redundancy means storing the same fact more than once. It wastes space, but the real damage is that the copies can drift apart. In a single “everything in one table” design, redundancy causes three kinds of anomaly. The table below is the shop’s order spreadsheet after the first clean-up step (1NF), with one row per product in an order. Try each anomaly:

AnomalyWhat goes wrongRoot cause
UpdateChanging one fact means changing many rows; miss one and the data contradicts itself.The same fact is stored in several rows.
InsertionYou cannot record one fact without inventing another (a product without an order).Unrelated facts share a primary key.
DeletionDeleting one fact accidentally destroys others (the last order of a customer).Unrelated facts live in the same row.

Key idea

Normalisation removes anomalies by making sure each fact is stored exactly once, in the table whose key it depends on. The tool for finding “what depends on what” is the functional dependency.

Functional dependencies

Attribute Y is functionally dependent on attribute(s) X, written X → Y, if each value of X is always associated with exactly one value of Y. X is called the determinant.

  • email → phone: knowing a customer’s e-mail tells you their (single) phone number.
  • product → price: each product has one price.
  • (order_no, product) → qty: you need both to know how many were ordered.
  • product → qty does not hold: the same product is ordered in different quantities.

Dependencies come from business rules, not from sample data

Five rows can disprove a dependency (two rows with the same X but different Y) but can never prove one. In the fruit-shop data four customers share one phone number, so phone → customer is false. Ask the client what is always true.

Three kinds of dependency

When the primary key is (order_no, product):

full
A non-key attribute depends on the whole key: (order_no, product) → qty. This is what we want.
partial
A non-key attribute depends on part of a composite key: order_no → order_date. Breaks 2NF.
transitive
A non-key attribute depends on another non-key attribute: supplier → supplier_phone (key → product → supplier → supplier_phone). Breaks 3NF.

Normalising step by step: UNF → 3NF

FormRuleHow to get there
UNFUnnormalised: cells may hold several values, groups of values repeat, no key.—
1NFEvery cell holds a single (atomic) value; no repeating groups; each row identified by a primary key.Split multi-part values into columns; give each repeated item its own row; choose a key.
2NF1NF, and no partial dependency: every non-key attribute depends on the whole key.Move attributes that depend on part of the key into a new table with that part as its key.
3NF2NF, and no transitive dependency: no non-key attribute depends on another non-key attribute.Move the dependent attributes into a new table keyed by their determinant; leave a foreign key behind.

Memory aid

In 3NF every non-key attribute depends on the key (1NF), the whole key (2NF), and nothing but the key (3NF).

Beyond 3NF, and when to denormalise

There are more normal forms than three. Each removes a rarer kind of redundancy:

FormRemovesExample
BCNF (Boyce–Codd)Any dependency whose determinant is not a candidate key(student, module) → tutor where each tutor teaches only one module (tutor → module). This is 3NF but not BCNF.
4NFIndependent multi-valued facts stored togetherA table of (employee, skill, language): skills and languages are unrelated lists.
5NFJoin dependencies (data that can only be rebuilt from three or more projections)Rare in practice.
6NF, DKNFTheoretical forms used in specialist (e.g. temporal) databases—

For most business systems 3NF (or BCNF) is the practical target, and 3NF is what the assessment asks for.

Denormalisation deliberately re-introduces redundancy to speed up reads, for example storing an order_total so reports do not have to add up items. It must be a conscious, documented decision, because you take back the anomaly risk. A view (Week 3) usually gives the convenience without the redundancy.

ER modelling concepts

An entity–relationship (ER) model describes the things a business needs to keep data about and how they relate. It is drawn as an ER diagram (ERD) before any SQL is written.

Entity
A thing of interest with its own identity: CUSTOMER, PRODUCT, ORDERS. (An entity type is the category; an instance is one occurrence, such as Jane.)
Attribute
A property of an entity. It can be simple or composite (an address made of street and postcode), single- or multi-valued (several phone numbers), and stored or derived (order total = Σ quantity × unit price).
Key attribute
An attribute that uniquely identifies each instance.
Relationship
An association between entities: a customer places orders. Its degree is the number of entity types involved: unary (an employee manages employees), binary (most relationships) or ternary.
Weak entity
An entity that cannot be identified without its owner, e.g. INVENTORY exists only for a PRODUCT.

A unary (recursive) relationship

In a unary relationship an entity is related to itself, playing two roles. The classic example comes from the original Week 1 database: the EMP table, where each employee’s mgr column holds the empno of their manager. Each employee (as a manager) manages zero or many employees; each employee (as a subordinate) is managed by zero or one employee, since the president has none.

Cardinality and participation

Each end of a relationship has two numbers:

  • Maximum (cardinality): one or many. This gives the relationship type: 1:1, 1:N or M:N.
  • Minimum (participation / optionality): zero (optional, partial participation) or one (mandatory, total participation).

Read a relationship in both directions, starting each sentence with “Each”:

Reading CUSTOMER — places — ORDERS

Each customer places zero or many orders (a new customer may not have ordered yet).
Each order is placed by exactly one customer (an order cannot exist without its customer).

Crow’s Foot and Chen notation

Both notations describe the same model. Chen (Peter Chen, 1976) is conceptual: it shows entities, attributes and relationships without implementation detail. Crow’s Foot (also called Information Engineering notation) is usually logical: boxes look like tables and list keys and foreign keys. It is the default in tools such as MySQL Workbench, Lucidchart and draw.io. This module uses Crow’s Foot by default; you should be able to read both.

ElementCrow’s FootChen

AttributesListed inside the box, often with data typesOvals connected to the entity
Primary keyMarked PK (and often underlined)Attribute name underlined
Foreign keyShown and marked FKNot shown: the relationship implies it
RelationshipA line, often labelled with a verbDiamond containing a verb
Maximum (one / many)A bar | for one, a crow’s foot for many, drawn at the line end1, N or M written beside each entity
Minimum (optional / mandatory)A circle ○ for zero, a bar | for one, drawn just outside the maximum symbolSingle line = partial participation; double line = total participation
Many-to-manyUsually resolved into a junction (associative) entityDrawn directly; the diamond can own attributes
Weak entity / identifying relationshipA table whose PK includes the owner’s key. Here the line is solid for an identifying relationship and dashed for a non-identifying one (the Coronel & Morris and MySQL Workbench convention)Double rectangle, joined to its owner by a double-diamond identifying relationship

Look-across reading

In both notations the symbol next to an entity says how many of that entity relate to one instance of the entity at the other end. The crow’s foot beside ORDERS means “many orders per customer”. Some textbooks use a (min,max) variant of Chen that is read the opposite way, and some slides and tools mix the two styles (a Chen diamond on a line with crow’s-foot ends). Always check the key on a diagram, and use one notation consistently in your own work.

One-to-one (1:1)

Each customer has zero or one account; each account belongs to exactly one customer. Toggle the notation to compare: the optional side becomes a circle in Crow’s Foot and a single line in Chen. The Crow’s Foot line is dashed because the relationship is non-identifying: account_id, not customer_id, identifies an account.

One-to-many (1:N)

The most common relationship. Each customer places zero or many orders; each order is placed by exactly one customer. In Chen, ORDERS has a double line (total participation) because every order must have a customer.

Many-to-many (M:N)

An order contains one or many products; a product appears in zero or many orders. Chen draws this directly, and the relationship owns attributes (quantity, unit price) that belong to neither entity alone.

Why INVENTORY is a weak entity in the Chen diagram

A weak entity has no key of its own: it is identified through its owner. An inventory record means nothing without the product it counts, and the database identifies it by the product’s key (inventory.product_id is the whole primary key). In Chen notation this is shown three ways:

  • INVENTORY is a double rectangle (weak entity);
  • HAS_STOCK is a double diamond (the identifying relationship that supplies the key);
  • INVENTORY has a double line to HAS_STOCK, because a weak entity always has total participation in its identifying relationship.

The cardinality is 1:1, so INVENTORY needs no partial key (the dashed-underlined discriminator that a weak entity has when one owner can have several, such as a room number within a building). PRODUCT’s double line is a business rule: every product must have a stock record.

A legitimate alternative

Conceptually you could also treat qty_in_stock, reorder_level and last_restocked as ordinary attributes of PRODUCT, and only split them into a separate table at the logical level for practical reasons. Both models are defensible. What matters in your report is that the diagram, the reasoning and the SQL agree.

From conceptual (Chen) to logical (Crow’s Foot)

The two diagrams above are the same design at two levels. Chen records what the business needs; Crow’s Foot records how it is stored in tables. Moving from one to the other is a set of mechanical rules:

Look at how the cardinalities move when CONTAINS becomes ORDER_ITEM. In Chen, “each order contains one or many products” and “each product appears in zero or many orders”. In Crow’s Foot each of these readings moves onto one of the new lines, at the ORDER_ITEM end:

  • ORDERS – ORDER_ITEM (bars at ORDERS, bar + crow’s foot at ORDER_ITEM): each order has one or many order items (the “1” minimum stays with the order);
  • PRODUCT – ORDER_ITEM (bars at PRODUCT, circle + crow’s foot at ORDER_ITEM): each product appears as zero or many order items;
  • each order item belongs to exactly one order and refers to exactly one product, because its two FKs are NOT NULL parts of its key.

What a diagram promises versus what SQLite enforces

Some minimums in the diagram are business rules that foreign keys alone cannot enforce: “an order has at least one item” and “every product has a stock record”. Note them in your design. Week 2 shows how triggers enforce rules like these.

Mapping an ER diagram to tables

  1. Each strong entity becomes a table. Simple attributes become columns; the key becomes the PRIMARY KEY.
  2. Composite attributes are split into their parts (address_line, postcode).
  3. Multi-valued attributes move to their own table, e.g. customer_phone(customer_id, phone) if a customer could have several numbers.
  4. 1:N: put a foreign key in the table on the many side (orders.customer_id). Make it NOT NULL when participation on that side is total.
  5. 1:1: put the foreign key on the optional or dependent side and add UNIQUE (user_account.customer_id). Without UNIQUE it would be 1:N.
  6. M:N: create a junction table holding both foreign keys, usually as a composite primary key. The relationship’s attributes become its columns.
  7. Weak entity: its primary key includes the owner’s key (inventory.product_id is both PK and FK).
  8. Derived attributes are normally not stored. Calculate them in queries or views (Week 3).

Here is rule 6 applied: the many-to-many from the previous section, resolved with order_item.


CREATE TABLE order_item (
    order_id    INTEGER NOT NULL
                REFERENCES orders (order_id)
                ON UPDATE CASCADE ON DELETE CASCADE,
    product_id  INTEGER NOT NULL
                REFERENCES product (product_id)
                ON UPDATE CASCADE ON DELETE RESTRICT,
    quantity    INTEGER NOT NULL CHECK (quantity > 0),
    unit_price  REAL    NOT NULL CHECK (unit_price >= 0),
    PRIMARY KEY (order_id, product_id)          -- one row per product per order
);

Building the database in SQLite

The full script is schema_v1.sql (see Resources). Each table follows the mapping rules. Here are three of them:


CREATE TABLE customer (
    customer_id   INTEGER PRIMARY KEY,                    -- surrogate key, auto-assigned
    first_name    TEXT    NOT NULL,
    last_name     TEXT    NOT NULL,
    email         TEXT    NOT NULL UNIQUE,                -- alternate (candidate) key
    phone         TEXT,
    address_line  TEXT    NOT NULL,
    postcode      TEXT    NOT NULL,
    registered_on TEXT    NOT NULL DEFAULT (date('now'))  -- ISO date 'YYYY-MM-DD'
);

CREATE TABLE user_account (
    account_id    INTEGER PRIMARY KEY,
    customer_id   INTEGER NOT NULL UNIQUE                 -- UNIQUE makes it 1:1
                  REFERENCES customer (customer_id)
                  ON UPDATE CASCADE ON DELETE CASCADE,
    username      TEXT    NOT NULL UNIQUE,
    password_hash TEXT    NOT NULL,                       -- never plain text (Week 6)
    created_at    TEXT    NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE orders (                                     -- ORDER is a reserved word
    order_id      INTEGER PRIMARY KEY,
    customer_id   INTEGER NOT NULL
                  REFERENCES customer (customer_id)
                  ON UPDATE CASCADE ON DELETE RESTRICT,
    order_date    TEXT    NOT NULL DEFAULT (date('now')),
    status        TEXT    NOT NULL DEFAULT 'Pending'
                  CHECK (status IN ('Pending','Paid','Shipped','Delivered','Cancelled'))
);

Choosing referential actions

The brief asks you to explain which referential integrity constraints you used and why. The ON DELETE / ON UPDATE action says what happens to child rows when the parent row changes:

ActionEffect when the parent is deletedUsed in the shop forWhy
RESTRICTThe delete is refused while children existorders → customer, product → category / supplier, order_item → productOrder history is a financial record; it must never vanish because a customer or product was removed.
CASCADEThe children are deleted tooorder_item → orders, inventory → product, user_account → customerThe child has no meaning without its parent (an order line without its order).

ON UPDATE CASCADE is used throughout, so if a key value ever changes, the foreign keys follow it.

Data types in SQLite

SQLite uses type affinity: a column’s declared type is a strong hint, not a strict rule. Use INTEGER, REAL, TEXT and BLOB, and store dates as ISO-8601 text ('2026-02-10') so they sort and compare correctly. Prices are REAL here for simplicity; production systems often store whole pence as INTEGER to avoid rounding errors.

Connecting from Python

The same database is used from Python with the built-in sqlite3 module. That is the foundation of the Tkinter application from Week 4. The full script is explore_shop_v1.py; here are the key parts, step by step.

1. Connect, and switch foreign keys on


import sqlite3
from pathlib import Path

# Find the database next to THIS script, wherever the folder is.
DB_PATH = Path(__file__).resolve().parent / "shop_v1.db"

def connect(path=DB_PATH):
    con = sqlite3.connect(path)
    con.row_factory = sqlite3.Row               # access columns by name: row["email"]
    con.execute("PRAGMA foreign_keys = ON")     # OFF by default, on EVERY connection
    return con

Path(__file__).resolve().parent replaces hard-coded paths such as C:\Users\Admin\Downloads\db1.db, which break on every other computer, including the marker’s.

2. Parameterised queries


email = "jane.morris@example.com"   # imagine this came from a Tkinter Entry box
rows = con.execute(
    """SELECT o.order_id, o.order_date, o.status
       FROM orders o JOIN customer c ON c.customer_id = o.customer_id
       WHERE c.email = ?
       ORDER BY o.order_date""",
    (email,),                         # a tuple: note the trailing comma
).fetchall()
for r in rows:
    print(r["order_id"], r["order_date"], r["status"])

Never build SQL by joining strings

Code such as "... WHERE email='" + email + "'" lets a user type SQL into your program: an SQL injection. Always use ? placeholders, from the very first line of your project. Week 10 shows the attack in detail.

3. Transactions and integrity errors


try:
    with con:                       # commit if the block succeeds, roll back if it fails
        con.execute("INSERT INTO orders (order_id, customer_id) VALUES (?, ?)", (9999, 999))
except sqlite3.IntegrityError as err:
    print("Blocked by FOREIGN KEY:", err)   # -> FOREIGN KEY constraint failed

Summary and next steps

  • Data becomes information through processing; a DBMS stores data and protects its integrity.
  • Relational databases suit structured, related data that needs transactions; NoSQL suits huge, flexible or graph-shaped data.
  • Redundancy causes update, insertion and deletion anomalies. Normalisation stores each fact once.
  • 1NF: atomic values and a key. 2NF: no partial dependencies. 3NF: no transitive dependencies.
  • ER diagrams show entities, attributes and relationships, each with a cardinality and participation. Crow’s Foot is logical and shows keys; Chen is conceptual and shows relationships as diamonds.
  • Mapping: 1:N → FK on the many side; 1:1 → FK + UNIQUE; M:N → junction table.
  • In SQLite always run PRAGMA foreign_keys = ON, and in Python always use ? placeholders.

Activity 1: Warm-up

Discuss in pairs (10 minutes)

  1. Describe a one-to-one, a one-to-many and a many-to-many relationship, each with an example that is not from the Online Shop.
  2. Give two strengths and two weaknesses of relational databases.
  3. What do SQL and NoSQL databases have in common, and how do they differ?
  4. Keys. Suggest a primary key for Product, Order, Customer and Sales person. Why not just use the business or person name?
  5. Track and artist. Can a music track belong to more than one artist? Can an artist have more than one track? What kind of relationship is this, and how would you store it?
  6. Fill the gaps with “relational” or “NoSQL”:
    • Which databases are table-based, and which are document-based?
    • Which are better for multi-row transactions?
    • Which are better for unstructured data?
    • “Strengths: strong data integrity, data organisation and security. Weaknesses: can be complex and expensive, and struggle with dynamic, unstructured data.”
    • “Strengths: scalability, simplicity, less code, easy maintenance. Weaknesses: less mature, less flexible queries.”
Model answers
  1. 1:1: a country has one capital city. 1:N: a football club has many players, and each player plays for one club (at a time). M:N: students take many modules, and each module has many students.
  2. Strengths: integrity constraints; powerful ad-hoc querying with JOINs; ACID transactions; mature tools and skills. Weaknesses: rigid schema changes; awkward for unstructured data; harder to scale across many servers.
  3. Both store and retrieve data persistently and support create/read/update/delete. They differ in data model (tables vs documents, key–value, columns or graphs), schema (fixed vs flexible), query language (standard SQL vs product-specific APIs) and scaling and consistency trade-offs.
  4. Product: a product code or surrogate product_id; Order: an order number; Customer: a surrogate customer_id (with e-mail as an alternate key); Sales person: an employee number. Names are not unique (two “James Smith”s), they change (marriage, rebranding) and they are long, so they make poor keys.
  5. Yes and yes: a track can feature several artists, and an artist records many tracks. It is many-to-many, implemented with a junction table such as track_artist(track_id, artist_id).
  6. Relational = table-based; NoSQL (document stores) = document-based. Relational is better for multi-row transactions; NoSQL for unstructured data. The first description is relational; the second is NoSQL.

Glossary

Anomaly
An inconsistency caused by redundancy when inserting, updating or deleting.
Associative entity
An entity (junction table) that resolves an M:N relationship.
Cardinality (ER)
The maximum number of instances on one side of a relationship (one or many).
Determinant
The left-hand side of a functional dependency.
Functional dependency
X → Y: each X value determines exactly one Y value.
Lossless decomposition
Splitting a table so that joining the parts gives back exactly the original data.
Participation
Whether every instance must take part in a relationship (total/mandatory) or need not (partial/optional).
Referential integrity
Every foreign key value matches an existing key in the referenced table.
Surrogate key
A system-generated key with no business meaning.
Weak entity
An entity identified partly or wholly through its owner entity.
